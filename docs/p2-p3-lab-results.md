# P2/P3 lab results (before the first hardware test) — 16 September 2026

Implemented everything from P2 (TLS and authentication) and P3 (encrypted service
discovery, keepalive, shutdown) that can run without the phone or the truck, so the
first vehicle visit can attempt G1, G2, and G3 in one trip. Verified against the
independent OpenAuto Prodigy receiver over lab TCP.

**This is lab evidence only.** No APK has been installed on the target phone, nothing
has run through the USB accessory driver, and no head unit has been contacted; the app
has run on ART only in an x86_64 emulator smoke test. G0–G5 remain open. In particular, the lab receiver does not verify our
certificate (Prodigy uses `SSL_VERIFY_NONE`), so nothing here says whether a factory
head unit accepts the generated source identity.

## Emulator smoke test (not device evidence)

`tools/emulator-image.sh` builds an optional image (Android Emulator 37.2.9 and the AOSP
API 36 x86_64 system image r02, archives checked against Google's manifest SHA-1 values)
and `tools/emulator-smoke.sh` runs a copy of the debug APK with an added x86_64
`libaap_jni.so` in a headless emulator, offline, with `debug.checkjni=1`. The run on
the `sdk_phone64_x86_64` 16 `BE2A.250530.026.D1` userdebug image passed:

- install with primary ABI x86_64; the native library loaded from the APK;
  "Late-enabling -Xcheck:jni" logged for both app launches;
- identity created and the TLS self-test passed on bionic
  (`tls_self_test=pass version=TLSv1.2 cipher=TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
  group=x25519`, `tls_library=OpenSSL 3.5.8 25 Aug 2026`), in about a second;
- Connect with Stop after `discovery` armed and reported `no accessory enumerated`;
  Stop ended `CANCELLED`; the saved report had `attempt_complete=true` and no key
  material;
- after a force-stop and relaunch, the same identity was loaded (`identity_created=false`);
- no crash, JNI error, or link error for the app in logcat.

It proves nothing about arm64, GrapheneOS, the accessory, or a head unit, and it cannot
pass G0. Two host-specific settings were needed: `-gpu swangle_indirect -feature -Vulkan`
(the default SwiftShader Vulkan path segfaulted at startup on this workstation) and
`-feature -ModemSimulator` (the network-less container cannot reach the modem simulator;
the emulator's radio HAL then aborts repeatedly, which the scan ignores).

## Controlled receiver runs (lab C1, lab G2/G3 mechanics)

`tools/lab-receiver.sh demo`, receiver requesting 1.1, fresh receiver credentials each
run, source identity persisted in the cache between runs:

| Run | Receiver | Source result |
| --- | --- | --- |
| Full, poll I/O, receiver pinned | Connecting → VersionExchange → TLSHandshake → ServiceDiscovery → Active → Disconnected (Normal) | `HOLD_COMPLETE` after 12 s, `last_completed_stage=discovery`, capabilities usable |
| Full, blocking-thread I/O | Same | Same; `io_reader=joined io_writer=joined io_descriptor=closed` |
| `LAB_STOP_AFTER=auth LAB_PEER=first-use` | Disconnected (TransportError) waiting for discovery | `STAGE_LIMIT`, `tls_peer_decision=first-use-accepted <receiver fingerprint>` |
| `LAB_PEER=mismatch` (wrong pin) | TLS handshake failed: "ssl/tls alert handshake failure" | `TLS_CERT_POLICY`, `tls_alerts=local:fatal:handshake_failure(40)`, `last_completed_stage=version` |
| `LAB_STOP_AFTER=version --io threads` | Disconnected in TLSHandshake | `STAGE_LIMIT`, ClientHello decoded without TLS |
| `LAB_REQUEST_VERSION=1.7` | Disconnected in VersionExchange | `VERSION_UNSUPPORTED`, nothing sent |
| `LAB_REQUEST_VERSION=1.7 … demo --profile legacy-1.5-any-minor` | "requested= 1.7 reported= 1.5 status= 0x0000", then through Active to Disconnected (Normal) | `HOLD_COMPLETE`, `requested_version=1.7`, `response_version=1.5`, capabilities usable |

Detail of the full run (source report and receiver log and trace):

- Version 1.1 → 1.5 MATCH, as in P1.1. The receiver's 1,533-byte ClientHello (OpenSSL
  3.5.7) offers TLS 1.3 and 1.2, 30 suites, and groups including X25519MLKEM768; the
  source negotiated **TLS 1.2 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` over x25519**.
  Handshake: 2,729 bytes in, 1,375 bytes out. The receiver's self-signed leaf matched
  the pin (`depth0:18:self-signed certificate` is recorded and expected without a CA).
- The receiver completed its handshake and sent **plaintext AUTH_COMPLETE `08 00`**
  (status 0), as its encryption policy predicts.
- The source sent one **encrypted ServiceDiscoveryRequest** (84 plaintext bytes:
  `device_name "OpenAutoAndroid"`, `device_brand "OpenAutoAndroid project"`, the session
  UUID). The receiver logged the decrypted request fields, and its trace records it.
  Its encrypted 127-byte response decrypted and validated: video channel 3 800x480@30,
  input channel 1 touch 800x480, `discovery_capabilities=usable`.
- Keepalive: the receiver's plaintext pings (every 5 s) were answered within 62–120 µs
  of receipt; the source's own pings (2 s after the receiver was last heard) were all
  answered, round trip under 0.4 ms.
- After the 12 s hold the source sent an encrypted ShutdownRequest (reason 1,
  USER_SELECTION); the receiver answered ByeByeResponse and disconnected Normal.

## Findings that change later work

- The lab receiver never checks the source certificate, and certificate acceptance by
  the head unit is the spec's main open question. G2 needs the factory unit.
- With a pinned-policy mismatch, OpenSSL's TLS 1.2 server sends `handshake_failure`
  (40), not `bad_certificate`. A head unit that reports a handshake failure right after
  its certificate may be seeing our pin policy, which the source report distinguishes.
- The receiver closes the connection immediately after ByeByeResponse. A transport close
  after our shutdown request therefore completes the hold (`HOLD_COMPLETE`) instead of
  counting as `IO_EOF`.
- `openssl-src` (the `openssl-sys` vendored build) lags the 3.5 LTS series by three
  patch releases and its 3.6 line ends support on 1 November 2026, hence the project's
  own pinned build.
- A head unit requesting 1.6 or later ends a `legacy-1.5` attempt at G1 with
  `VERSION_UNSUPPORTED`. The opt-in `legacy-1.5-any-minor` profile carried Prodigy's 1.7
  request through discovery in the lab, but whether a factory unit accepts a lower
  response is unknown.
- The baseline suite list is a guess until the factory ClientHello is recorded. A G2
  attempt that ends `TLS_NO_COMMON_SUITE` still records the offered suites, and
  `tls12-cbc-compat` is ready but must not be used without that evidence.

## Limitations and open items

- Nothing has run on the phone: arm64 ART loading of the larger library, RSA key
  generation time on its CPU, the TLS self-test on its bionic, the UI on GrapheneOS, and
  the accessory path through TLS are unverified (the x86_64 emulator covered the same
  code paths except the accessory). G0 must show `tls_self_test=pass`.
- The simulator shares framing and generated message types with the source; only the
  Prodigy runs are independent, and they cover one receiver's behavior over TCP.
- The Prodigy discovery response is minimal (two channels, no keycodes); the factory
  response will exercise more of the validation.
- Stop from the UI cancels immediately without a shutdown request. *(Changed in the P4
  slice: after TLS, in the hold or a projection stage, Stop now stops the stream and sends a
  shutdown request first, then releases the session after the ByeByeResponse or a 3 s grace
  period.)*
- The spec's JSON evidence bundle (`summary.json`, `events.jsonl`, `capabilities.json`)
  is not produced; reports remain `key=value` text with the same content.
- Background and screen-off behavior, channel opens, video, and input (P4) are not
  started.
